# 대학생 소비 기록 스와이프 가계부
## 프로그램 개발 명세서 v1.0

### 1. 프로젝트 개요

본 프로젝트는 금융 앱의 결제 알림을 자동으로 수집한 뒤, 사용자가 하루에 한 번 카드 형태로 소비 내역을 직접 검토하는 **Human-in-the-loop 기반 가계부 애플리케이션**이다.

기존 자동 가계부 서비스는 은행 출금, 간편결제 충전, 실제 결제를 서로 다른 소비로 판단하여 동일한 소비를 여러 번 기록하거나, 계좌 간 송금·정산 등을 실제 소비로 오인하는 문제가 존재한다.

본 서비스는 모든 금융 데이터를 완전히 자동으로 판단하는 대신, 시스템이 소비 후보를 수집·분류하고 사용자가 최종적으로 승인하도록 한다.

사용자는 매일 자신이 지정한 시간에 소비 후보 카드를 확인하며,

- 오른쪽 스와이프 → 실제 소비로 포함
- 왼쪽 스와이프 → 소비에서 제외
- 카드 터치 → 금액·가맹점·카테고리 수정
- 검토 종료 후 `+` 버튼 → 누락된 소비 직접 추가

방식으로 하루의 소비를 정산한다.

최종적으로 승인된 소비만 월간 캘린더와 통계에 반영한다.

---

# 2. 핵심 서비스 목표

서비스의 핵심 목표는 다음 세 가지이다.

**정확성**

금융 앱이 자동으로 기록한 내용을 그대로 신뢰하지 않고 실제 소비 여부를 사용자가 최종 확인하여 중복·오탐을 제거한다.

**낮은 입력 부담**

사용자가 모든 소비를 직접 작성하는 기존 수기 가계부와 달리 금융 알림을 자동 수집하고 사용자는 스와이프만으로 기록할 수 있도록 한다.

**소비 습관 형성**

하루에 한 번 자신의 소비를 직접 돌아보는 과정을 만들어 단순한 소비 기록 앱이 아니라 일종의 **Daily Consumption Review** 경험을 제공한다.

# 3. 주요 사용자 시나리오

사용자는 최초 실행 시 알림 접근 권한을 허용하고 하루 소비 검토 시간을 설정한다.

이후 사용자가 카카오페이, Toss, 카드 앱, 은행 앱 등을 통해 결제하면 Android의 `NotificationListenerService`가 관련 알림을 감지한다.

알림에서 다음 정보를 추출한다.

`결제 금액 / 가맹점명 / 결제 시각 / 알림 발생 앱`

필요한 경우 결제 직전 사용 앱과 위치 정보를 추가적인 메타데이터로 기록한다.

수집된 정보는 바로 실제 소비로 기록하지 않고 **소비 후보(Transaction Candidate)** 상태로 Room DB에 저장한다.

예를 들어 사용자가 카카오페이로 12,000원의 식사를 결제하여 다음과 같은 알림이 발생할 수 있다.

`은행 → 카카오페이 12,000원 출금`

`카카오페이 → 12,000원 충전`

`카카오페이 → OO식당 12,000원 결제`

시스템은 세 개의 Raw Event를 보존하면서 서로 연관된 거래일 가능성을 계산하고 사용자에게는 실제 소비로 판단되는 카드와 함께 **“중복 가능성”**을 표시한다.

저녁 10시 등 사용자가 설정한 시간이 되면 다음과 같은 알림을 제공한다.

> 오늘 6개의 소비 기록이 있어요.  
> 오늘 쓴 돈을 정리해볼까요?

사용자가 앱을 열면 카드 검토가 시작된다.

모든 카드를 처리하면 승인된 소비만 Expense Record로 확정되고 해당 날짜의 소비 금액과 카테고리별 통계가 갱신된다.

# 4. 전체 시스템 구조

```text
카드 / 은행 / 간편결제 앱
          │
          ▼
NotificationListenerService
          │
          ▼
Notification Parser
          │
          ├── 금액
          ├── 가맹점명
          ├── 시간
          └── 발생 앱
          │
          ▼
Raw Payment Event
          │
          ├──────── UsageStatsManager
          │            └─ 직전 사용 앱
          │
          └──────── Location
                       └─ 결제 위치
          │
          ▼
Transaction Candidate Generator
          │
          ├── 중복 탐지
          ├── 송금/충전 탐지
          └── 카테고리 분류
          │
          ▼
Room Database
          │
          ▼
Daily Review
          │
    ┌─────┴─────┐
    ▼           ▼
Right Swipe   Left Swipe
소비 포함       소비 제외
    │
    ▼
Confirmed Expense
    │
    ├── Calendar
    ├── Statistics
    └── Personalization History
```

Android의 `NotificationListenerService`는 새로운 알림이 게시되거나 제거되는 이벤트를 앱이 수신할 수 있도록 제공되는 공식 API이다.

# 5. 기능 요구사항

## FR-01. 금융 알림 자동 수집

앱은 `NotificationListenerService`를 사용하여 사용자가 허용한 앱에서 발생한 알림을 감지한다.

지원 대상 예시:

`카카오페이 / Toss / 삼성카드 / 신한카드 / 국민카드 / 은행 앱`

모든 알림을 저장하지 않고 등록된 금융 앱 패키지의 알림만 처리한다.

---

## FR-02. 결제 정보 파싱

알림의 `title`, `text`, `bigText`, `packageName`을 분석하여 다음 정보를 추출한다.

```text
amount
merchantName
transactionTime
sourcePackage
notificationText
```

앱별 알림 형식이 다르므로 앱별 Parser를 분리한다.

```text
NotificationParser
 ├─ TossParser
 ├─ KakaoPayParser
 ├─ ShinhanParser
 ├─ KBParser
 └─ GenericParser
```

파싱에 실패한 알림은 삭제하지 않고 `PARSE_FAILED` 상태로 저장하여 개발·확장 과정에서 대응할 수 있도록 한다.

---

# 6. 결제 맥락 수집

## FR-03. 직전 사용 앱 분석

`UsageStatsManager`를 이용하여 결제 시점 직전 사용한 앱을 조회한다.

예:

```text
배달의민족 실행
↓
카카오페이 결제
↓
12,000원 결제 알림
```

이라면

```text
foregroundApp = com.sample.baemin
```

정보를 저장한다.

`UsageStatsManager.queryEvents()`를 이용한 다른 앱의 사용 기록 조회에는 `PACKAGE_USAGE_STATS` 접근 권한이 필요하다.

단, 해당 정보는 절대적인 결제 근거가 아니라 **분류를 돕는 Context 정보**로만 사용한다.

---

## FR-04. 위치 기반 장소 추론

위치 권한을 허용한 사용자에 한해서 결제 주변 위치를 기록할 수 있다.

가맹점명과 좌표를 Kakao Local API의 장소 키워드 검색에 전달한다.

```text
query = 스타벅스
x = longitude
y = latitude
radius = 500m
```

응답에서 다음 정보를 얻는다.

```text
place_name
category_name
category_group
distance
```

Kakao Local API는 키워드와 좌표를 이용한 주변 장소 검색 및 장소 카테고리 정보를 제공한다.

단, 앱이 백그라운드 상태인 시점에 위치를 자동 수집하려면 별도의 백그라운드 위치 권한과 정책 고려가 필요하므로 해커톤 MVP에서는 **선택적 기능**으로 구현한다.

# 7. 데이터 처리 구조

이 서비스에서는 반드시 다음 두 종류의 데이터를 분리한다.

### Raw Payment Event

금융 앱에서 실제로 발생한 원본 알림이다.

사용자가 소비에서 제외하더라도 삭제하지 않는다.

### Expense Record

사용자가 실제 소비라고 최종적으로 승인한 기록이다.

월간 소비량 및 통계에는 이 데이터만 사용한다.

이 구조를 사용하면 여러 금융 앱에서 동일한 결제를 감지하더라도 실제 소비 통계가 중복되는 것을 방지할 수 있다.

---

# 8. DB 설계

Android Jetpack의 Room을 이용해 로컬 DB를 구성한다. Room은 SQLite 위에서 동작하며 SQL 검증, Entity/DAO 관리 등을 제공한다.

### RawPaymentEvent

```text
id: Long
packageName: String
rawTitle: String
rawText: String

amount: Long?
merchant: String?
detectedAt: Long

foregroundApp: String?

latitude: Double?
longitude: Double?

fingerprint: String

parseStatus:
    SUCCESS
    FAILED
```

### Transaction

```text
id: Long

rawEventId: Long?

amount: Long
merchant: String
transactionTime: Long

predictedCategory: String
finalCategory: String?

classificationSource:
    RULE
    APP
    LOCATION
    AI
    USER

status:
    PENDING
    INCLUDED
    EXCLUDED

source:
    NOTIFICATION
    MANUAL

duplicateGroupId: String?

memo: String?

confirmedAt: Long?
```

### CorrectionHistory

```text
id: Long

merchant: String
foregroundApp: String?

predictedCategory: String
correctedCategory: String

createdAt: Long
```

사용자의 수정 결과를 이후 개인화 분류에 활용한다.

### UserSettings

```text
reviewHour: Int
reviewMinute: Int

notificationEnabled: Boolean
locationEnabled: Boolean
aiEnabled: Boolean
```

# 9. 중복·오탐 탐지

본 서비스의 핵심 기능 중 하나이다.

각 Raw Event에 다음 정보를 기반으로 fingerprint를 생성한다.

```text
merchant
amount
time window
source app
```

예를 들어

```text
금액 동일
+
1~3분 이내 발생
+
유사 가맹점
```

조건을 만족하는 이벤트가 여러 개 존재한다면 하나의 `duplicateGroupId`로 묶는다.

또한 다음 키워드가 포함된 거래는 실제 소비가 아닐 가능성이 높은 것으로 표시한다.

```text
충전
송금
계좌이체
내 계좌
입금
출금
정산
```

단, 시스템이 자동 삭제하지는 않는다.

카드에

`중복 가능성이 있어요`

또는

`계좌 이동으로 추정돼요`

라는 Badge를 표시하고 최종 판단은 사용자가 한다.

# 10. 소비 카테고리 분류

카테고리는 다음과 같이 정의한다.

```text
식비
카페
교통
쇼핑
생활
문화/여가
교육
의료
여행
구독
기타
```

분류는 우선순위를 가진다.

```text
① 사용자의 과거 수정 기록
        ↓
② 명확한 앱 정보
        ↓
③ 가맹점 Rule
        ↓
④ 위치 / Kakao Place
        ↓
⑤ On-device AI
        ↓
⑥ 기타
```

예:

```text
배달의민족
→ 식비

무신사
→ 쇼핑

CGV
→ 문화/여가
```

# 11. 사용자 개인화

사용자가

```text
스타벅스
AI 예측 → 식비
사용자 수정 → 카페
```

로 수정했다면 해당 기록을 `CorrectionHistory`에 저장한다.

이후 동일하거나 유사한 결제에서는 사용자 수정 기록을 가장 먼저 검색한다.

따라서 모델 자체를 재학습하지 않더라도 사용할수록 사용자의 카테고리 기준에 가까워진다.

이는 엄밀하게는 **모델 학습**이 아니라 사용자 수정 이력을 활용한 **Few-shot / Retrieval 기반 개인화**이다.

# 12. 온디바이스 AI

규칙 기반 방식으로 분류할 수 없는 거래는 LiteRT-LM 기반의 Gemma 4 E2B를 이용하여 로컬에서 분류할 수 있다.

예시 입력:

```text
가맹점: 성균문구
결제 금액: 8,500원
시간: 15:32
직전 앱: 없음

과거 사용자 기록:
교보문고 → 교육
알파문구 → 교육

다음 카테고리 중 하나만 선택:
식비, 카페, 교통, 쇼핑, 생활,
문화/여가, 교육, 의료, 여행, 구독, 기타
```

출력:

```text
교육
```

목록 외의 출력은 강제로 `기타` 처리한다.

LiteRT-LM은 Android 등에서 LLM을 온디바이스로 실행할 수 있도록 지원하고 현재 Gemma 4 E2B도 지원 모델로 안내하고 있다. 다만 공식 예시에 표시된 Gemma-4-E2B 모델 크기가 약 **2.58GB**이므로 해커톤 MVP에서는 설치 크기와 기기 성능을 반드시 고려해야 한다.

따라서 MVP에서는

```text
Rule
→ User History
→ App Context
```

까지 구현하고 Gemma 기반 분류는 고성능 Android 기기에서 작동하는 **AI Demo 기능**으로 구현하는 것을 권장한다.

```text
오늘 소비 6건이 아직 기다리고 있어요 👀
오늘 하루 쓴 돈을 정리해볼까요?
```

라는 알림을 제공한다.

정확히 특정 분에 실행할 필요가 없다면 Android의 일반 Alarm 또는 WorkManager 기반으로 구현한다. WorkManager는 앱 종료나 기기 재시작 이후에도 필요한 예약 작업을 관리하기 위한 Android 권장 API이다.

정확한 시각의 Alarm은 Android 버전에 따라 별도의 특수 권한이 필요할 수 있으므로 본 서비스에서는 ±수십 분 수준의 검토 알림을 허용하는 것을 기본 설계로 한다.

# 18. 게이미피케이션

MVP 이후 캐릭터 기반 소비 관리 기능을 추가한다.

```text
600,000원
```

예상 지출이 증가할수록 캐릭터의 상태가 변화한다.

예:

```text

😊

예산 근접
😐

예산 초과 예상
😵
```

카테고리별 소비 특성도 캐릭터 속성으로 표현할 수 있다.

```text

→ 배달 봉투

쇼핑 소비 증가
→ 쇼핑백
```

# 25. 서비스 핵심 정의

본 프로젝트의 차별점은 단순히 금융 알림을 수집하는 것이 아니다.

기존 가계부가 추구하는

**“완전 자동화”**

대신

**“자동 수집 + 사용자 3초 판단”**

이라는 방식을 사용한다.

즉,

> AI와 규칙 기반 시스템은 소비 기록을 대신 결정하는 것이 아니라 사용자가 판단하기 좋은 상태까지 정리한다.

사용자는 매일 짧은 스와이프 과정을 통해 자신의 소비를 직접 확인한다.

결과적으로

**자동 가계부의 편리함**

+

**수기 가계부의 정확성**

+

**매일 소비를 돌아보는 습관**

을 동시에 제공하는 것을 본 서비스의 최종 목표로 한다.

# 26. 구현 현황 — 사용 기술과 장점

해커톤 기간 동안 실제로 구현한 내용과, 각 기술 선택이 주는 장점을 정리한다. (대상 기기: Galaxy S25+, 온디바이스 전용)

## 26.1 기술 스택

```text
언어/UI    : Kotlin, Jetpack Compose (Material 3)
로컬 DB    : Room (SQLite) — DB 버전 5, 수동 마이그레이션
알림 수집  : NotificationListenerService
결제 맥락  : UsageStatsManager (직전 사용 앱)
예약 작업  : WorkManager (하루 검토 알림)
온디바이스 AI : Gemma 4 E2B + LiteRT-LM (GPU 우선, CPU 대체)
비동기     : Kotlin Coroutines / Flow
설계       : 단일 Activity + 수동 DI, 화면별 ViewModel
```

**장점**
- 전부 온디바이스로 동작해 **네트워크 없이, 금융 데이터가 기기 밖으로 나가지 않는다**(Local-first, 명세서 20장).
- Compose로 화면을 선언형으로 작성해 상태(소비 목록·그래프)가 바뀌면 UI가 자동으로 갱신된다.

## 26.2 알림 수집 · 파싱 (FR-01, FR-02)

- `NotificationListenerService`로 등록된 금융 앱(토스·카카오뱅크·카드사 등)과, 카드 알림이 문자·카카오톡으로 오는 경우를 함께 감지한다. 발신자가 금융기관처럼 보일 때만 수집한다.
- 앱별 형식이 달라 범용 파서로 **금액·가맹점·수입/지출**을 추출하고, 실패한 알림은 삭제하지 않고 상태로 남긴다.
- **장점:** 사용자가 아무 입력을 하지 않아도 결제 후보가 자동으로 쌓인다(낮은 입력 부담).
- 개발·시연용으로 **가짜 결제 알림 생성**과 **알림 진단 로그**를 만들어, 실제 결제 없이도 전체 흐름을 재현하고 실제 알림 형식을 수집·분석할 수 있다.

## 26.3 데이터 분리 · 중복/이체 탐지 (7·9장)

- **원본 알림(Raw Event)** 과 **소비 기록(Transaction)** 을 분리 저장한다. 제외해도 원본은 지우지 않는다.
- 같은 금액이 ±3분 내 여러 번 오면 하나의 그룹으로 묶어 **"중복 가능성"**, 충전·송금·출금 키워드가 있으면 **"계좌 이동으로 추정"** 배지를 표시한다. 시스템이 자동 삭제하지 않고 판단은 사용자가 한다.
- **장점:** 은행 출금·간편결제 충전·실제 결제가 각각 기록되는 **중복·오탐 문제**를 사용자가 3초 판단으로 해결한다(핵심 Demo).

## 26.4 스와이프 검토 · 정산 (14장)

- 카드를 **오른쪽(반영)/왼쪽(제외)/위쪽(정산)** 으로 스와이프한다. 정산은 인원수를 입력하면 **내 몫만** 소비로 기록하고 원래 금액과 인원을 함께 저장한다.
- 스와이프 직후 **실행 취소**, 검토 완료 후 **누락 소비 직접 추가**를 지원한다.
- **장점:** 하루 소비를 짧은 손동작으로 정산하는 **Daily Consumption Review** 경험을 그대로 구현했다.

## 26.5 카테고리 분류 (10·11·12장)

분류는 우선순위 체인으로 동작한다.

```text
① 사용자의 과거 수정 기록(가맹점 기준)
② 결제 직전 사용한 앱 (UsageStats, 예: 스타벅스 앱 → 카페)
③ 가맹점 Rule (약 150개 키워드)
④ 온디바이스 AI (Gemma) — 규칙으로 못 정한 지출만
```

- 사용자가 카테고리를 고치면 기록해 두고, 이후 같은 가맹점에 자동 적용한다(재학습이 아닌 **Retrieval 기반 개인화**).
- Gemma는 분류용과 챗봇용이 **하나의 엔진을 공유**하여 약 2.6GB 모델을 프로세스당 한 번만 로드한다.
- **장점:** 알림에 법인명만 찍혀 무엇을 샀는지 모를 때도 **직전 앱 정보**로 카테고리를 메워, 분류 공백을 줄인다.

## 26.6 고양이 챗봇 — AI 소비 피드백 (19장)

- 로컬 DB에서 집계한 **소비 요약**(이번 달·지난달 합계, 카테고리별, 요일·시간대, 목표 대비 속도, 최근 결제)을 Gemma에 전달해 소비 습관 조언을 생성한다. 숫자 계산은 앱이 미리 끝내 모델이 수치를 지어내지 않게 한다.
- **장점:** "쇼핑을 절반 줄였다면?" 같은 질문에 **실제 내 데이터로** 답하고 절약 챌린지를 제안한다. 모두 기기 안에서 처리된다.

## 26.7 리포트 · 목표 (18장 확장)

- 월별로 **좌우 슬라이드**하며 최근 3개월을 비교한다. 각 달마다 목표 도넛, 카테고리 막대, **소비 속도 그래프**를 보여준다.
- 목표 소비 속도선은 직선이 아니라 **사용자의 과거 요일별 소비 패턴**을 반영한 곡선으로 그린다.
- 소비 내역은 **목록 / 카테고리(2열 폴더) / 캘린더** 세 가지로 전환해 본다.
- **장점:** 단순 합계를 넘어, 내 소비 리듬에 맞춘 **목표 속도**와 카테고리별 비교를 직관적으로 제공한다.

## 26.8 검토 알림 (17장)

- `WorkManager` 일회성 작업을 매일 이어 붙여, 설정한 시간에 남은 소비가 있으면 알림을 보낸다. 재부팅·앱 종료 후에도 유지되며 정확한 시각 특수 권한이 필요 없다.

## 26.9 온디바이스 AI 선택 근거

- 처음 ML Kit의 Gemini Nano를 시도했으나 대상 기기(S25+)에서 자유 프롬프트 기능이 지원되지 않아(`FEATURE_NOT_FOUND`), **Gemma 4 E2B + LiteRT-LM**으로 구현했다. S25+의 GPU에서 약 5초 내 로드되고 분류는 0.2초 내, 챗봇 답변은 수 초 내로 응답한다.
- 모델은 용량이 커 앱에 포함하지 않고 기기에 미리 넣어 사용한다. 외부에 배포하는 시연 버전은 **클라우드 LLM으로 교체**할 수 있도록 분류·챗봇을 공통 인터페이스 뒤에 두었다.

## 26.10 소비 분석 고도화 (Local-first 분석 엔진)

분석 로직은 Android 의존성이 없는 순수 Kotlin `analysis` 패키지에 두고 JUnit으로 검증한다. 모든 수치는 기기 안에서 코드가 계산하며, 네트워크를 쓰지 않고 카테고리를 자동으로 바꾸지 않는다(표시 전용).

- **가맹점명 정규화 (`MerchantNormalizer`):** "스타벅스 강남R점", "(주)스타벅스코리아"처럼 지점·법인·특수문자 표기를 떼어내 같은 가게를 한 키로 모은다. 단 "편의점·백화점"처럼 업종을 뜻하는 단어는 지키고, 영문은 소문자로 통일한다. 수정 기록 저장·조회가 이 키를 쓰며, 기존 기록도 1회 백필한다.
  - **장점:** 지점이 달라도 수정 기록이 공유되어 개인화가 더 자주 적중한다.
- **분류 정확도 통계 (`AccuracyStats`):** 검토가 끝난 거래 중 예측과 사용자 최종 선택이 다른 **수정률**을 전체·분류 소스별(규칙/직전 앱/AI/내 기록)로 집계해 설정 화면에 보여준다.
  - **장점:** 분류 품질을 숫자로 추적해, 어느 단계를 개선해야 할지 근거를 남긴다.
- **반복 결제 탐지 (`RecurringDetector`):** 정규화 가맹점으로 묶어 3건 이상·금액 ±10% 이내·주기(주간 7±2일 또는 월간 28~33일)를 만족하면 구독으로 본다. 대표 금액·주기·다음 예상일·월 환산액을 리포트 "매달 자동으로 나가는 돈" 카드에 표시한다.
  - **장점:** 흩어진 결제 속에서 고정 지출을 자동으로 드러내 예산을 세우기 쉽다.
- **이상 소비 탐지 (`AnomalyDetector`):** 카테고리별 최근 7일 합계를 이전 8개 주간 구간의 기준선과 비교한다. 이상치에 둔감한 중앙값·MAD 기반 robust z(≥3.5, MAD가 0이면 "현재 ≥ 중앙값×2")를 쓰고, 절대 격차가 1만 원 이상일 때만 알린다("이번 주 배달이 평소의 2.3배").
  - **장점:** 한 번의 큰 지출에 휘둘리지 않는 통계로, 정말 평소와 다른 주만 짚어준다.
- **월말 지출 예측 (`MonthForecaster`):** 최근 60일의 요일별 지출 풀에서 남은 날을 무작위로 1,000번 뽑아 월말 지출의 P10~P90 범위를 추정한다. 반복 결제는 풀에서 빼고 남은 기간 예정분을 확정 금액으로 더해 이중 계산을 막는다. 소비 속도 그래프에 반투명 밴드로 얹고, 14일 미만이면 "데이터를 모으는 중"을 보여준다.
  - **장점:** "이 속도면 월말 OO~OO원"처럼 단정이 아닌 **범위**로 안내해, 목표 초과 위험을 미리 체감하게 한다.
- **인사이트 후보 엔진 (`InsightEngine`):** 카테고리 증가·심야 소비·주말 몰림·소액 다빈도·최대 단건·반복 결제·이상 소비·목표 초과 예측을 후보로 만들고, **의외성(변화율, 상한 3) × 금액 가중치(log10)**로 점수를 매겨 상위 3개만 리포트에 보여준다. 같은 카테고리 중복은 하나로 합친다.
  - **장점:** 수많은 수치 중 **지금 가장 의미 있는 세 가지**만 골라, 고양이 챗봇이 말로 풀어 줄 재료로 쓴다.
- **숫자 검증기 (`NumberVerifier`):** 모델 답변에서 원·만/천·%·배·건/번 표현을 뽑아 앱이 계산한 허용 숫자와 대조한다(천·만 단위 반올림 허용). 허용 밖 숫자가 있으면 "제공된 숫자만 쓰라"고 1회 재생성하고, 그래도 실패하면 템플릿 문장으로 대체한다.
  - **장점:** 작은 모델이 **숫자를 지어내는 환각**을 사후에 차단해, 가계부가 틀린 금액을 말하지 않게 한다.
- **함수 호출 챗봇 (`ChatTools` · `CatAdvisor.answer`):** 고정 요약을 통째로 넘기던 방식을, 모델이 질문에 맞는 **도구를 JSON으로 고르면 앱이 숫자를 계산**하고 모델은 그 결과만으로 문장을 쓰는 구조로 바꿨다. 도구는 요약·기간 비교·자주 간 곳·시간 패턴·가정 절약·고정 지출·인사이트 8개 이하로 두고, 상대 날짜는 오늘 날짜로 해석한 뒤 코드에서 재검증하며, 모델이 엉뚱한 도구·인자를 내면 키워드 라우터로 대체한다. 모든 답변은 숫자 검증기를 통과한다.
  - **기술 선택:** LiteRT-LM에 네이티브 함수 호출 API가 있으나, 작은 모델 신뢰도를 위해 **JSON 프로토콜**을 택했다(도구 선택은 결정적 샘플링, 답변 생성은 스트리밍).
  - **장점:** "배달 절반 줄이면 얼마 아껴?"처럼 **계산이 필요한 질문**에 정확한 수치로 답하면서도 모든 연산은 기기 안 Kotlin이 담당한다.
- **소비 성향 → 고양이 캐릭터 (`SpendingTendency`):** 사용자가 한 명이라 군집화 대신, 최근 30일의 **카테고리별 비중·심야 결제 비중·소액 결제 비중**을 특징 벡터로 만들어 미리 정의한 성향 원형(카페형·배달야식형·쇼핑형·생활교통형·균형형)과 코사인 유사도로 비교해 가장 가까운 성향을 고른다. 데이터가 14일 미만이면 균형형. 홈 화면에 "오늘의 소비 성향" 배지로 보여주고 18장 캐릭터 소품(커피·배달 봉투·쇼핑백 등)과 연결한다.
  - **장점:** 딱딱한 통계 대신 **캐릭터 성향**으로 소비 습관을 한눈에 요약해, 가계부에 애착을 갖게 한다.
