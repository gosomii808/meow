# 작업 요청: 소비분석 AI 고도화 (1단계 + 2단계)

## 0. 배경
우리 앱은 "대학생 소비 기록 스와이프 가계부"다. 명세서 26장 기준 현재 구현 상태는 다음과 같다.
- Kotlin, Jetpack Compose(Material 3), Room(DB 버전 5, 수동 마이그레이션), Coroutines/Flow, 단일 Activity + 수동 DI, 화면별 ViewModel
- 온디바이스 AI: Gemma 4 E2B + LiteRT-LM (GPU 우선, CPU 대체). 분류와 챗봇이 엔진 하나를 공유한다.
- 카테고리 분류 체인: ① 사용자 수정 기록(가맹점 기준) → ② 직전 사용 앱(UsageStats) → ③ 가맹점 Rule(약 150개 키워드) → ④ Gemma
- 고양이 챗봇: 앱이 집계한 소비 요약을 Gemma에 넘기고, Gemma는 문장만 만든다. 숫자 계산은 앱이 한다.
- 리포트: 월별 3개월 비교, 목표 도넛, 카테고리 막대, 소비 속도 그래프(요일별 패턴을 반영한 목표 곡선)

이번 작업의 목표는 소비분석의 품질을 높이는 것이다. 온디바이스와 Local-first 원칙은 반드시 유지한다.

## 1. 반드시 지킬 원칙
1. 네트워크를 쓰는 기능을 추가하지 않는다. 금융 데이터는 기기 밖으로 나가지 않는다.
2. 숫자 계산은 전부 Kotlin 코드가 한다. Gemma는 도구를 고르고 문장을 만드는 역할만 한다.
3. 기존 기능과 UI 흐름을 깨지 않는다. 새 기능은 기존 화면에 카드나 섹션을 추가하는 방식으로 붙인다.
4. Room 스키마를 바꾸면 버전 5→6 명시적 Migration을 작성한다. fallbackToDestructiveMigration은 절대 쓰지 않는다. 사용자 데이터가 날아간다.
5. 분석 로직은 Android 의존성이 없는 순수 Kotlin 패키지(예: `analysis`)에 두고 JUnit 단위 테스트를 작성한다.
6. 기존 수동 DI 패턴을 따른다. Hilt 같은 새 DI 프레임워크를 도입하지 않는다.
7. 새 라이브러리 의존성은 추가 전에 이유와 용량을 먼저 알려주고 승인을 받는다.
8. 분석 대상은 status = INCLUDED인 거래만이다. 정산 거래는 내 몫으로 기록된 금액을 사용한다.
9. 무거운 계산은 Dispatchers.Default에서 실행하고, UI는 Flow로 갱신한다.

먼저 코드베이스를 탐색해서 아래 항목별로 수정·추가할 파일과 클래스를 정리한 계획을 보여줘. 내가 확인한 뒤에 구현을 시작한다. 구현은 아래 순서대로 하고, 항목 하나가 끝날 때마다 빌드와 테스트 통과를 확인한 뒤 다음 항목으로 넘어간다.

A. 1-4 가맹점명 정규화 (다른 기능의 기반)
B. 측정: 사용자 수정률 로깅
C. 2-1 반복 결제 탐지
D. 2-2 이상 소비 탐지
E. 2-3 월말 지출 예측 범위

J. 2-4 소비 성향 → 고양이 캐릭터 (시간이 남으면)

## A. 1-4 가맹점명 정규화
`MerchantNormalizer.normalize(raw: String): String`
- 제거 대상: (주), ㈜, 주식회사, 유한회사, 괄호 안 내용, 특수문자, 연속 공백
- 지점 접미사 제거: "강남R점", "역삼역점", "2호점", "본점", "지점"처럼 끝에 붙은 지점 표기. 단, "점"으로 끝나는 모든 단어를 지우면 안 된다. 예: "편의점", "백화점"은 유지한다. 지점 패턴(지명/숫자/알파벳 + 점, 호점, 지점)만 제거한다.
- 영문은 소문자로 통일한다.
- 정규화 결과가 빈 문자열이면 원본을 trim해서 반환한다.
- 수정 기록 저장과 조회 양쪽에 적용한다. 기존 CorrectionHistory 데이터에도 정규화 값을 채우는 마이그레이션 또는 백필을 작성한다.
- 테스트 케이스: "스타벅스 강남R점"→"스타벅스", "(주)스타벅스코리아"→"스타벅스코리아", "GS25 역삼역점"→"gs25", "CU편의점"→"cu편의점", "이마트 본점"→"이마트"

## B. 측정: 사용자 수정률
성능 개선을 숫자로 보여주기 위한 지표다.
- 검토가 끝난 거래 중 predictedCategory와 finalCategory가 다른 비율을 계산한다.
- classificationSource별로도 수정률을 나눠서 집계한다. (RULE, APP, AI, 사용자 기록 등)
- 설정 화면 하단이나 디버그 메뉴에 "분류 정확도 통계"로 간단히 표시한다.

## C. 2-1 반복 결제(구독) 탐지
`RecurringDetector.detect(transactions): List<RecurringPayment>`
- 정규화된 가맹점명으로 묶는다. 같은 가맹점 거래가 3건 이상일 때만 판단한다.
- 금액 조건: 모든 금액이 그 그룹 금액 중앙값의 ±10% 이내
- 주기 조건: 연속 결제 간격의 중앙값이 주간(7일 ±2일) 또는 월간(28~33일)
- 결과 필드: 가맹점, 대표 금액, 주기(WEEKLY/MONTHLY), 마지막 결제일, 다음 예상 결제일, 월 환산 금액
- 리포트 화면에 "매달 자동으로 나가는 돈" 카드를 추가한다. 예: "3건 · 월 42,000원"
- finalCategory를 자동으로 바꾸지 않는다. 표시만 한다.

## D. 2-2 이상 소비 탐지
`AnomalyDetector.detect(transactions, today): List<Anomaly>`
- 카테고리별로 "오늘 포함 최근 7일 합계"를 계산하고, 그 이전 8개 구간(7일 단위)의 합계를 기준선으로 쓴다.
- 기준선 구간이 4개 미만이면 판단하지 않는다.
- robust z = 0.6745 × (현재값 − 중앙값) / MAD. z ≥ 3.5이면 이상으로 본다.
- MAD가 0이면 대신 "현재값 ≥ 중앙값 × 2" 조건을 쓴다.
- 노이즈 방지를 위해 현재값과 중앙값의 차이가 10,000원 이상일 때만 이상으로 본다.
- 결과 필드: 카테고리, 현재값, 기준 중앙값, 배수(현재/중앙값), z값
- 문구 예: "이번 주 배달이 평소의 2.3배예요"

## E. 2-3 월말 지출 예측 범위
`MonthForecaster.forecast(transactions, today, recurring): Forecast`
- 최근 60일의 일별 지출 합계를 만든다. 지출이 없는 날은 0으로 포함한다.
- 요일별 풀을 만든다. 남은 날짜마다 같은 요일의 과거 일별 합계 중 하나를 무작위로 뽑는다.
- 이 시뮬레이션을 1,000번 반복하고, (이번 달 현재 지출 + 시뮬레이션 합)의 P10/P50/P90을 구한다.
- C에서 찾은 반복 결제 중 이번 달 남은 기간에 예정된 것은 확정 금액으로 더한다. 이중 계산을 막기 위해, 반복 결제 거래는 부트스트랩 풀에서 빼고 일별 합계를 만든다.
- 테스트 재현성을 위해 Random에 시드를 받을 수 있게 한다.
- 데이터가 14일 미만이면 범위를 표시하지 않고 "데이터를 모으는 중이에요"를 보여준다.
- 소비 속도 그래프에 P10~P90 구간을 반투명 밴드로 추가한다. 목표 금액과 비교한 문구도 보여준다. 예: "이 속도면 월말 58만~66만 원 (목표 60만 원)"

## F. 1-2 인사이트 후보 엔진
`InsightEngine.generate(transactions, today, goal): List<Insight>`
규칙으로 인사이트 후보를 만들고 점수를 매긴 뒤 상위 3개만 반환한다.

후보 생성기:
- 카테고리 증가: 최근 7일과 이전 4주 주평균의 비교
- 심야 소비: 22시~04시 결제의 비중과 금액
- 주말 몰림: 주말 지출 비중
- 소액 다빈도: 10,000원 이하 결제의 건수와 합계
- 최대 단건 결제
- C의 반복 결제, D의 이상 소비, E의 목표 초과 예측

점수와 필터:
- 점수 = 의외성 × 금액 가중치
  - 의외성: 기준 대비 변화율의 절댓값. 상한은 3으로 잘라낸다.
  - 금액 가중치: log10(관련 금액 + 1)
- 거래가 3건 미만인 후보는 버린다.
- 같은 카테고리의 후보가 중복되면 점수가 높은 하나만 남긴다.

각 Insight에는 타입, 한 줄 요약, 근거 숫자를 담는다. 근거 숫자는 "12,000원", "2.3배", "5번"처럼 화면 표시용으로 포맷된 문자열로 넣는다.
챗봇의 "이번 달 조언"과 리포트 요약에는 이 상위 3개를 Gemma에 넘겨 고양이 말투로 풀어 쓰게 한다.

## G. 1-3 숫자 검증기
`NumberVerifier.verify(answer: String, allowed: Set<String>): Result`
- Gemma 답변에서 숫자 표현을 추출한다. 처리할 형식: "12,000원", "12000원", "1만 2천원", "1.2만원", "23%", "2.3배", "5번", "3건"
- 금액은 원 단위 Long으로 정규화해서 비교한다.
- 허용 집합은 이번 응답에 Gemma에게 준 도구 결과와 인사이트의 모든 숫자다. 천 원·만 원 단위 반올림 값도 허용한다.
- 처리 순서:
  1. 허용 집합에 없는 숫자가 있으면, "제공된 숫자만 사용하라"는 지시를 강화해서 1회 재생성한다.
  2. 그래도 실패하면 템플릿 문장으로 대체한다.
- 검증 실패 사례는 로그로 남긴다.

## H. 1-1 함수 호출 챗봇
지금은 고정 요약을 통째로 넘기는 구조다. 이것을 Gemma가 질문에 맞는 도구를 골라 호출하는 구조로 바꾼다.

먼저 확인할 것: 프로젝트에서 쓰는 LiteRT-LM 버전에 Kotlin용 네이티브 도구 호출(tool use / function calling) API가 있는지 확인하고 알려줘.
- 있으면 그 API를 쓴다.
- 없거나 불안정하면 JSON 방식으로 구현한다. Gemma에게 {"tool": "...", "args": {...}} 또는 {"tool": "none"}만 출력하게 하고, 파싱해서 실행한 뒤, 결과를 넣어 두 번째 호출로 답변을 생성한다.

도구 목록 (작은 모델의 정확도를 위해 8개 이하로 유지):
- get_spending_summary(start_date, end_date, category?): 총액, 건수, 카테고리별 합계
- compare_periods(a_start, a_end, b_start, b_end, category?): 두 기간 비교와 증감률
- get_top_merchants(start_date, end_date, category?, limit): 많이 쓴 가맹점
- get_time_pattern(start_date, end_date, category?): 요일별·시간대별 지출
- simulate_whatif(category, reduce_ratio): 이번 달 해당 카테고리를 그 비율만큼 줄였을 때의 절약액과 예상 월말 지출(E 활용)
- get_recurring_payments(): C 결과
- get_insights(): F 결과 상위 3개
- none: 도구 없이 일반 대화

구현 규칙:
- "지난주", "이번 달", "어제" 같은 상대 날짜는 시스템 프롬프트에 오늘 날짜를 넣어서 해석하게 하고, 실제 날짜 계산은 코드에서 한 번 더 검증한다.
- 질문 하나당 도구 호출은 최대 2회로 제한한다.
- 도구 이름이나 인자가 잘못되면 키워드 기반 라우터로 대체한다. 예: "구독"→get_recurring_payments, "줄이면"→simulate_whatif
- 카테고리 인자는 앱의 11개 카테고리 목록 중 하나로 강제한다. 목록에 없으면 null로 처리한다.
- 모든 최종 답변은 G의 숫자 검증기를 통과해야 한다.
- 고양이 말투, 반말, 3문장 이내로 답하게 한다.
- 테스트 질문 예시:
  - "이번 달 카페에 얼마 썼어?"
  - "지난달이랑 비교하면 어때?"
  - "배달 절반 줄이면 얼마 아껴?"
  - "매달 나가는 돈 뭐 있어?"
  - "안녕"

## I. 2-5 유사 가맹점 개인화
지금은 "교보문고→교육"으로 고쳐도 같은 이름에만 적용된다. 이것을 "알파문구", "성균문구"처럼 비슷한 가맹점에도 적용되게 만든다.

임베더 인터페이스 `MerchantEmbedder { fun embed(text: String): FloatArray }`와 구현체 두 개를 만든다.
- 구현 1, 기본값: 문자 2-gram과 3-gram 기반 TF-IDF 벡터. 순수 Kotlin으로 의존성 없이 구현한다.
- 구현 2, 선택: EmbeddingGemma(308M)
  - LiteRT에서 실행 가능한 모델 파일과 토크나이저가 있는지 먼저 조사해서 보고한다. Hugging Face의 litert-community 등을 확인한다.
  - 통합 비용이 크면 이번에는 구현하지 않고, 인터페이스만 맞춰 둔다.
  - 구현할 경우 모델 카드에 적힌 작업별 프롬프트 접두어를 그대로 사용한다.
  - Gemma 4 E2B와 메모리를 함께 쓰므로 지연 로드하고, 쓰지 않을 때는 해제한다.

분류 체인 변경: ① 정확 일치 수정 기록 → ①' 유사 수정 기록(새로 추가) → ② 직전 앱 → ③ Rule → ④ Gemma
- ①'의 방식: 수정 기록 임베딩과 코사인 유사도를 비교해 상위 3개를 찾는다. 유사도가 임계값 이상인 것들의 다수결로 카테고리를 정한다.
- 임계값은 상수로 두고, 기본값은 TF-IDF 0.6 / EmbeddingGemma 0.8에서 시작한다. B의 수정률을 보며 조정한다.
- 수정 기록의 임베딩은 DB에 캐시한다. FloatArray를 ByteArray로 바꿔 BLOB으로 저장한다.
- classificationSource에 유사 기록 값(예: HISTORY_SIMILAR)을 추가한다. Room에 enum이 어떻게 저장되는지 확인하고, 기존 데이터가 깨지지 않게 한다.
- 카드의 "AI가 ○○로 분류했어요" 문구에 근거를 보여준다. 예: "비슷한 '알파문구'를 교육으로 고쳤던 기록을 참고했어요"

## J. 2-4 소비 성향 → 고양이 캐릭터 (선택)
사용자가 한 명이라 여러 사용자 간 군집화는 불가능하다. 대신 미리 정의한 성향 원형(centroid)과 비교해 가장 가까운 성향을 고르는 방식으로 구현한다.
- 특징 벡터: 최근 30일의 카테고리별 지출 비중, 심야 결제 비중, 소액 결제 비중
- 성향 원형: 카페형, 배달·야식형, 쇼핑형, 생활·교통형, 균형형
- 결과를 명세서 18장의 캐릭터 소품과 연결한다. 카페형은 손에 커피, 배달·야식형은 배달 봉투, 쇼핑형은 쇼핑백.
- 데이터가 14일 미만이면 균형형으로 둔다.
